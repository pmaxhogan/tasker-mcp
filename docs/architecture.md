# Architecture

tasker-mcp has two halves. A small Tasker project on the phone exposes an
authenticated HTTP API. A TypeScript MCP server on the desktop talks to it and
does all the real work: parsing Tasker's XML, editing it, validating it, and
turning it into MCP tools.

## Data flow

```
 MCP client (Claude, ...)
        |  stdio, JSON-RPC
        v
 +--------------------------------------------------+
 | tasker-mcp (Node)                                |
 |  src/tools  ->  src/edit  ->  src/model          |
 |                      |            |              |
 |                  src/spec     src/xml            |
 |  src/docs   snapshots   config/adb               |
 |                      |                           |
 |                  src/client                      |
 +----------------------|---------------------------+
                        |  HTTP + bearer token
                        |  (adb forward tcp:1821, or http://phone:1821)
                        v
 +--------------------------------------------------+
 | Phone: Tasker                                    |
 |  profile "TaskerMCP HTTP" (HTTP Request event)   |
 |    -> task TaskerMCP.Dispatch (JavaScript)       |
 |         /backup /import /config /run /vars ...   |
 +--------------------------------------------------+
```

Docs follow a separate path: GitHub Actions scrapes the userguide into the
`docs-data` branch, and `src/docs` downloads it on first use into the local cache.

## Layers

- `src/xml`: a hand-written, lossless XML DOM. `serialize(parse(s)) === s` byte
  for byte (see [xml-roundtrip.md](xml-roundtrip.md)), so a one-action edit never
  reformats the rest of a 2 MB backup.
- `src/model`: a JSON view over the DOM (`TaskerDoc`): projects, profiles, tasks,
  scenes, with actions decoded into named args. Conversions go both ways.
- `src/spec`: the action table (arg ids, names, types) built from the MapTasker
  action list plus strings extracted from the Tasker APK, and validation against
  it. The format itself is described in
  [tasker-xml-format.md](tasker-xml-format.md).
- `src/edit`: plan and splice. Edits are planned against the current document
  and spliced into it as XML blocks; `verify` re-reads the result.
- `src/client`: the phone HTTP client, with errors that carry a fix hint.
- `src/tools`: one module per tool group. Each exports `register(server, ctx)`
  and gets everything from a `ToolContext` (client, snapshots, docs, write
  policy), so tests inject fakes. Per-task `tasker_*` tools are registered
  dynamically from tasks tagged `#mcp`.
- `src/docs`: lazy, disk-cached userguide search.
- `src/snapshots.ts`: snapshot store under `~/.tasker-mcp/snapshots`, newest 20
  kept.
- `src/config.ts`, `src/adb.ts`: flags and env vars, the write policy, and the
  `adb forward` / device selection logic.

## The mutation pipeline

Every mutating tool follows the same steps:

1. **Policy.** Check the write policy for each object name and kind; refuse
   whole-configuration imports when they are off.
2. **Snapshot.** Fetch a fresh backup and save it before touching anything.
3. **Plan.** Build the change against that backup (replace-by-name for tasks).
4. **Validate.** Check actions against the spec table. Unknown action codes pass
   through as raw XML.
5. **Apply.** A task change is `POST /import` with a single-task TaskerData XML;
   Tasker replaces a same-named task in place. Profile, project, rename, move,
   and delete changes build a full configuration from the fresh backup and send
   it with `POST /config`, then wait for the phone to answer `/ping` again.
6. **Re-fetch and verify.** Read the configuration back and confirm the change
   landed as planned.
7. **Duplicate cleanup.** If Tasker produced a duplicate (for example a task
   imported under a second id), remove it through the same path.

## The phone project

`tasker/TaskerMCP.prj.xml` is generated by `scripts/build-phone-project.ts` from
`tasker/js/*.js`. It holds one catch-all profile (HTTP Request event on port
1821 with empty method and path) whose entry task, `TaskerMCP.Dispatch`, is a
JavaScript dispatcher: it checks the bearer token, routes by method and path,
runs the needed Tasker actions, and answers with an HTTP Response. Route table and
verified device behaviour: [../tasker/README.md](../tasker/README.md).

## CI

- **CI** (`ci.yml`), on every push and PR:
  - lint and typecheck: ESLint, Prettier check, the ASCII dash check, `tsc`;
  - test with coverage and the coverage ratchet (fails if coverage dropped more
    than 0.5 points);
  - build, then a stdio smoke test that sends `initialize` and expects a
    `serverInfo` reply;
  - gitleaks;
  - `npm publish --dry-run`.
- **Publish** (`publish.yml`), on pushes to `main`: computes the next patch from
  the registry; real publish only when npm auth is configured, else a dry run.
- **APK spec sync** (`apk-spec-sync.yml`), weekly: downloads the newest Tasker
  trial APK, regenerates `data/`, and opens a PR only when the output differs.
- **Docs sync** (`docs-sync.yml`), weekly: scrapes the userguide and force-pushes
  it to the orphan `docs-data` branch when the index changed.
- **Dependabot auto-merge**: approves and auto-merges minor and patch bumps once
  required checks pass.

## Why it is built this way

- **XML round trip instead of a native API.** Tasker exposes no API for
  structure. Its Data Backup export and Import Data action are the only complete
  read and write paths, so the server works on XML.
- **A lossless DOM.** Tasker XML is large, and users diff it. Rewriting only what
  changed keeps edits small and avoids spurious churn or data loss.
- **Tasker's HTTP Request event, not a separate Android app.** It needs no extra
  install or permissions beyond Tasker. The cost is that Tasker honours one HTTP
  Request event per port and path, hence one catch-all profile and a JavaScript
  dispatcher.
- **Desktop does the XML work.** The phone only serves backup, import, and run.
  Parsing, validation, and the action table live where they can be tested and
  updated without touching the phone.
- **Config replace for profile, project, and delete edits.** Import Data only
  accepts a task or a whole configuration, so those edits send a full
  configuration with only the intended change. That is why the monitor restarts
  for about 3 seconds, and why `TASKER_ALLOW_CONFIG_IMPORT` exists as a switch.
- **One reusable scratch task for `run_actions`.** Deleting a task needs a
  whole-configuration import, so `run_actions` replaces `TaskerMCP.Scratch` in
  place instead of creating and deleting throwaway tasks.
- **Snapshot first, verify after.** The agent can be wrong and so can Tasker.
  Snapshots make every change reversible; readback catches imports that silently
  did nothing.
- **Never hand-author arg layouts.** Action arg layouts vary in odd ways. The
  spec table comes from MapTasker and the APK, and anything not covered is
  harvested from the GUI (see [../CONTRIBUTING.md](../CONTRIBUTING.md)).
- **Unknown action codes allowed.** Tasker adds actions often; the server should
  not block ones it has not seen.
- **Docs outside the package.** The userguide is (c) joaoapps, so it lives on a
  separate branch, is downloaded on demand, and is never in the npm tarball.
- **Per-task tools via `#mcp`.** Follows the dceluis/tasker-mcp convention so
  existing tagged tasks work, and lets a user hand the agent a few vetted tasks
  instead of full access.
- **Write policy by name prefix.** A real phone holds real automations; a prefix
  allow list is simple to reason about and enforced in one place
  (`ToolContext.assertWritable`).
- **adb forward by default.** The token is the only authentication, so the
  default path keeps the port on localhost.
